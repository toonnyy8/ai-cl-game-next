# Divergences

BEVY_PORT §2: "A Lisp bug is ported as a bug and listed in `docs/bevy/DIVERGENCES.md` for the user to rule on after parity." This file
lists those bugs, and separately the places where the port knowingly differs from the Lisp on paths no trace reaches.

## 1. Lisp bugs ported as bugs

**None found in M1** (the sim core, Kenpachi, Ichigo; checked 2026-11-27 against the Task 1-14 reports and reviews, and the port's
comments). Every quirk the M1 tasks met is either intended by the Lisp or invisible to play. They are kept bit for bit and listed here
so nobody "fixes" them by accident. **M2 found three real bugs**: MC-SEARCH's UCB macro, a played cinematic's DURING forms writing sim
state, and the human's device read inside a rollout (their rows below):

| Where | What the Lisp does | Why it is kept, not a bug |
|---|---|---|
| rules.lisp DIR-YAW vs engine YAW-TO (`math::dir_yaw` / `yaw_to`) | two yaw functions: CL ATAN (a double atan2 rounded to single) and atan2f; they differ in the last bit | DIR-YAW's docstring: the seeded replays were recorded with it, "so the sim keeps it" |
| hazards.lisp HAZARD-CONNECTED during HIT-APPLY (`Match.hz_dead`, hazards.rs 289) | writes a hazard's struct after DESTROY-ENTITY took it (PENDING holds the struct) | the struct is unreachable after its hit; nothing reads the write |
| tools/simgate/trial.lisp `:p2-reishi` / `:p1-reishi` (`cl::Num`) | writes `(f32 x)` into the fixnum Reishi slot, so Reishi becomes a float and flows through CL contagion | the trial runner's, not the game's; a real match never has a float Reishi. The port carries `Num` so trial traces replay. A float damage under a float Reishi is `unported!` (unreached); TIME-UP-WINNER takes the float (`rules::time_up_winner`, M2 Task 3) |
| tuning.lisp `*stun-blow-away*` NIL | the hidden stun still adds and decays but never blows anyone away | the user's ruling (DEVLOG §173); the docstring says so |
| mcts-lite.lisp MC-SEARCH's UCB macro (`cpu/mcts_lite.rs` `Lite::search`; found in M2 Task 8) | the macro's `(dotimes (a 10) …)` captures the caller's `a`: the tree's second level is called with BASE `(* 10 a)`, which is evaluated inside that loop, so the opponent's reply B is scored from `n2` / `sum2` at index 11 B (the reply's own diagonal) instead of 10 A + B, while the update after the rollout writes 10 A + B | a bug (the intended row is A's), but every recorded match plays it: ported as is (the closure's BASE is a function of the loop variable); without it cvc-ii-s1's first job picks another second action at step 325. Decoupled UCT (HARD's `:duct`, BASE 0) is unaffected. **To rule on:** fixing it (BASE `(* 10 a)` bound once per call, the reply scored from its own row) changes how a NORMAL CPU picks its second action in every full-sim MCTS decision: the play of every match that queues a job (in the gate every trace with a NORMAL or EASY Ichigo CPU: the nine KI / IK / II cvc traces, cvctag-ii / -ik, cvc-ki-s1-easy and vs-cpu-ichigo, first at cvc-ii-s1 step 325), which would be re-recorded from a fixed Lisp with cvc-tag.txt's II / IK lines; KK, cvc-ki-s1-hard (its HARD Ichigo is in `*mc-off-at*`), vs-cpu and vs-learn queue no job and stay. The user decides whether the intended search plays better (a playtest) |
| a played cinematic's DURING forms (engine/lisp/cine.lisp CINE-DRAW; ken.lisp / ken-look.lisp KE-KK-AT and KE-KK-YAW in DURING; `ken::cine::draw`, `cine::cine_draw`; found in M2 Task 9) | the draw mode, "cosmetic" by cine.lisp's header, runs once per rendered frame after the frame's steps and moves the actors' TRANSFORMs (Kenpachi's KR / ZH / Z-1 / S-1 / S-2 Kikons: the victim looking round, blown away; Kenpachi through him). So the H / B lines inside such a cinematic depend on the frames drawn (none in turbo), and a victim's DURING yaw outlives the cinematic (CINE-END gives back only the CINE-SAVE'd places) until RESET-ROUND faces them again | a bug against the header's intent, invisible to a match's result (the places are given back; RESET-ROUND or MATCH-OVER faces both after a Kikon), but in every played cinematic: ported as is (run by `flow::frame` unless turbo); without it vs-cpu diverges at step 6203. **To rule on:** fixing it (the draw mode writes only looks, as cine.lisp's header says) changes the actors' places during and after a played Kikon cinematic outside turbo: the H / B lines of vs-cpu from step 6203, vs-learn from 2771 and vs-cpu-ichigo (two KEN-Z-KIKON1 and two KEN-S-KIKON1 played, their DURING arms run), and possibly the next exchange if a victim's DURING yaw outlives the cinematic; never the cvc gate (turbo skips cinematics). **The frame rate changes the sim:** DURING runs once per *rendered* frame, not per 60 Hz step, so on a display that is not at 60 Hz (a 120 Hz or 144 Hz screen draws two-plus frames per step, a 30 Hz one half), or whenever frames are dropped, the actors' places inside a played Kikon cinematic differ, and with them the sim state after it (a victim's leftover yaw, so possibly the next exchange): the same inputs give a different match on another screen, and a recorded replay is only exact at the frame rate it was recorded at. What players see: the victim no longer keeps the cinematic's last facing until the next round reset. The port would then also stop calling `cine::cine_draw` from the sim (M3 then owns it as a look) |
| cpu-mcts.lisp MC-FULL-ROLL / strategy-glue.lisp STRAT-ROLL's stand-in brain for a human (`flow::InRollout`, `PilotInput::rollout_read`; M2 Task 9) | the stand-in's VPAD-BEGIN-STEP! (and a rollout's PILOT-READ) calls the human's vpad reader, which writes his held keys before AI-PRESS-WRITE!: a held key is pressed afresh each rollout step, and a button the stand-in holds is released and pressed again each step | not what the stand-in (a CPU playing the human's seat) is for; ported as is. Keyed by vs-cpu-ichigo (M2 final review I1: a human Kenpachi vs a NORMAL Ichigo CPU): 19 jobs, 38 rollouts, 3,010 device reads inside them, the human holding a button on 29 of its 38 job steps, `replay --live` OK; also host test `vs_device_writes_in_rollouts`. **To rule on:** fixing it (no device read inside a rollout: the stand-in plays the human's seat from its own presses only) changes the scores of a CPU's full-sim jobs in a VS CPU match against a human who holds a key while the CPU searches, hence that CPU's choices there; of the recorded traces only vs-cpu-ichigo would change (re-recorded from a fixed Lisp). The user decides whether a VS CPU opponent should search without the human's held keys |
| dead branches (RUN-STEP's guard branch, TSUKI-STEP's `(dash :tsuki-step)` clause, MOVE-COMMANDS' `:kikon` / `:f` / `:sig` / `:sp1` / `:sp2` clauses, the echo window's test for an existing `:blade`) | code no live data reaches | ported where cheap, or dropped with a comment; no behaviour either way |

## 2. Port differences on paths no trace reaches

Not Lisp bugs. These are spots where the Rust stops (a panic, `unreachable!`) or reads differently, only on a path no live data or gate
trace reaches today. Fix each before the milestone that reaches it.

| Where | Lisp | Port | Reached by |
|---|---|---|---|
| `kit::find_move` | FIND-MOVE returns the registry's move (`*moves*`) | the first name match in moves.json: the kit's copy (KE-Z-N2A hs 10 vs the registry's 8); 7 Yamamoto names have a `var/` entry first | M4 (Hisagi / Yamamoto); no M1 caller differs |
| `ken/hooks.rs` `as_pick`'s `nth_as` | `(nth i as)` past the end is NIL, so the pointer's default AS | `expect` panics | a kit with a short `:as` (none) |
| `ichigo/clones.rs` `flag_sym` | an echo window keeps any flag (a keyword) | panics on a flag outside its 19 | a new window flag |
| `combat.rs` `HwRef::Perfect` | `*perfect-hw*` built once at load | read from the knobs live | a debug command changing knobs mid-run |
| `debug::force_form` | ignores SET-FORM's result | `&&`s it (false only on an unported hook) | an unported form hook |
| `core_sim::core_next_as` | any length of `:as-by-press` | widens on the stack, up to 16 entries, and panics past that | a kit with more than 16 |
| `components::Few` (a runtime HITWIN's volumes / flags, an ICC's queued presses / replays, the clone lists; M2 Task 10) | lists of any length | inline, panics past 2 volumes, 4 flags, 4 presses, 16 clones, 16 queued replays. | `fighter/moves.rs` `HookFn::Cine` | a cinematic name in a hook slot | `unreachable!` | none in the data |
